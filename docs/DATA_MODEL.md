# Data model

Status: **partly implemented.** Tables marked *implemented* exist in `apps/server/src/db/schema.ts` with migrations in `apps/server/drizzle/`; the rest is the Phase 1 draft and is revised by the ticket that implements each table. Table names are plural `snake_case` (`accounts`, `sessions`, `audit_log`); the draft names below follow the same convention when implemented.

| Table       | Status                  |
| ----------- | ----------------------- |
| `accounts`  | implemented (ticket 1.1) |
| `sessions`  | implemented (ticket 1.1) |
| `audit_log` | implemented (ticket 1.1) |
| `characters` | implemented (ticket 1.3) |
| `item_instances` | implemented (tickets 1.6 / 1.7; item model v2 in 3.1) |
| `activities` | implemented (ticket 1.6) |

## Principles
- **Content is code, state is data.** Classes, enemies, areas, item bases, affixes and loot tables are versioned definitions in `@worldforge/game-core`, referenced from the database by string id (`class_id = 'warrior'`). The database stores only player and world *state*.
- **Server-authoritative.** Every row below is written only by the server. Values derived from content (final stats, power score) are computed, not stored, unless needed for leaderboards.
- **Integers for value.** Gold and other currencies are `bigint`; no floats for anything that is spent or compared.
- **Auditability.** Value-changing operations write a ledger/audit row in the same transaction.
- IDs are UUIDv7 (`uuid`), generated by the server (`uuidv7()` in `src/db/uuid.ts`); timestamps `timestamptz` in UTC. Soft deletes only where noted.
- Value-changing writes go through `withTransaction()` and write their audit row with `writeAudit(tx, …)` in the same transaction.

## Entities

### accounts — implemented (1.1)
| Column          | Type        | Notes                                                        |
| --------------- | ----------- | ------------------------------------------------------------ |
| id              | uuid PK     | UUIDv7                                                       |
| email           | text        | stored trimmed as entered; unique on `lower(email)`          |
| display_name    | text        | unique on `lower(display_name)`                              |
| password_hash   | text        | argon2id PHC string (`$argon2id$v=19$m=19456,t=2,p=1$…`), written by 1.2 |
| character_slots | smallint    | default 2 (GDD §5.3), `CHECK (>= 0)`; per account, so slots can be granted later |
| active_character_id | uuid FK? | → `characters.id` `ON DELETE SET NULL`; the last selected character (ticket 1.3). Only ever set to one of the account's own characters (checked by the server) |
| guide           | jsonb       | default `{"steps":[],"dismissed":false}`; first-session guide (ticket 2.7): game-core `GuideState` (steps seen done, in guide order, and whether it was closed). UI state only, grants nothing; per account so it follows the player across devices |
| created_at      | timestamptz | default `now()`                                              |
| updated_at      | timestamptz | default `now()`; set by the server on update                 |

Owner decision (GDD v0.3): real registration/login from Phase 1, no dev identity, so the draft's `auth_kind` column and separate `account_credential` table were dropped. If OAuth arrives later, it gets an `account_identities` table (provider, subject) and `password_hash` becomes nullable.

### sessions — implemented (1.1)
| Column     | Type        | Notes                                                             |
| ---------- | ----------- | ----------------------------------------------------------------- |
| id         | text PK     | SHA-256 hex of a random 256-bit token; the raw token only lives in the cookie |
| account_id | uuid FK     | → `accounts.id` `ON DELETE CASCADE`, indexed                      |
| created_at | timestamptz | default `now()`                                                   |
| expires_at | timestamptz | `CHECK (expires_at > created_at)`                                 |
| revoked_at | timestamptz | null while active; set on logout                                  |

A session is valid iff `revoked_at IS NULL AND expires_at > now()` (the server compares against its own clock). Login and registration insert a row (`created_at` = issue time, `expires_at` = + `SESSION_TTL_HOURS`); logout sets `revoked_at`. Pruning expired rows is left to a later maintenance job.

### characters — implemented (1.3)
| Column         | Type        | Notes                                            |
| -------------- | ----------- | ------------------------------------------------ |
| id             | uuid PK     | UUIDv7                                           |
| account_id     | uuid FK     | → `accounts.id` `ON DELETE CASCADE`, indexed. Count ≤ `accounts.character_slots`, enforced by the server under a `SELECT … FOR UPDATE` lock on the account row |
| name           | text        | trimmed as entered; unique on `lower(name)` across all accounts. Rules in game-core `validateCharacterName` (3–16 ASCII letters, one `'` or `-` between parts, a few reserved names) |
| class_id       | text        | game-core `ClassId`, validated by the server, immutable after creation. No DB `CHECK`, so adding a class needs no migration |
| appearance     | jsonb       | game-core `CharacterAppearance`: `{ banner }` (`ash`/`ember`/`moss`/`dusk`) |
| level          | integer     | default 1, `CHECK (>= 1)`                        |
| experience     | bigint      | default 0, `CHECK (>= 0)`; within the current level |
| gold           | bigint      | default 0, `CHECK (>= 0)`                        |
| farm_state     | jsonb?      | `{ seedSecret, cycleIndex, health, areaId? }` saved when the character's activity ends and restored when it starts again (ticket 1.9), so stop → start neither heals nor re-rolls. `areaId` (ticket 2.2) is the area of a cycle left unfinished by the stop; the next start replays that cycle there before travelling on. Never sent to clients |
| progress       | jsonb       | game-core `WorldProgress`, default `{"gravewardenDefeated": false}` (ticket 2.2). Unlock facts besides the level; written only by the server (the Gravewarden kill arrives with ticket 2.5). Ticket 3.6 adds `cryptTierCleared` (the deepest crypt tier cleared; absent before it, and a Gravewarden kill counts as tier I) |
| version        | integer     | default 0; optimistic concurrency counter for later value-changing writes |
| created_at / updated_at | timestamptz | default `now()`                         |

`rng_state` from the draft is not used: settlement RNG comes from a per-character secret and cycle index (see `activities` and `farm_state`). Characters cannot be deleted or renamed yet.

### audit_log — implemented (1.1)
Append-only (the server never updates or deletes rows) for valuable or security-relevant events (auth events, item grants of epic+, deletions, rewards).
| Column       | Type        | Notes                                                                 |
| ------------ | ----------- | --------------------------------------------------------------------- |
| id           | uuid PK     | UUIDv7, so rows sort by time                                          |
| account_id   | uuid FK?    | → `accounts.id` `ON DELETE SET NULL` (anonymous events, e.g. failed login for an unknown email; history survives account deletion) |
| character_id | uuid FK?    | → `characters.id` `ON DELETE SET NULL` (added by ticket 1.3)          |
| event        | text        | dotted name, e.g. `account.register`, `auth.login`, `auth.login_failed` |
| data         | jsonb       | default `{}`; small, non-secret context (never passwords or tokens)   |
| created_at   | timestamptz | default `now()`                                                       |

Indexes: `(account_id, created_at)`, `(event, created_at)`.

### item_instances — implemented (1.6 / 1.7; item model v2 in 3.1)
One owned item, created from a game-core `GeneratedItem`. Location is a column, not a separate table: `equipped_slot` null = in the inventory, otherwise equipped in that slot.
| Column        | Type        | Notes                                                              |
| ------------- | ----------- | ------------------------------------------------------------------ |
| id            | uuid PK     | UUIDv7                                                             |
| character_id  | uuid FK     | → `characters.id` `ON DELETE CASCADE`                              |
| base_id       | text        | game-core item base id                                             |
| rarity_id     | text        | game-core `RarityId`                                               |
| item_level    | integer     | check `>= 1`                                                       |
| affixes       | jsonb       | game-core `RolledAffix[]`, default `[]` (shape below)              |
| seed          | bigint      | generation seed (uint32), for audit and reproducibility            |
| equipped_slot | text?       | game-core `EquipmentSlotId`; unique per character when not null    |
| source        | text        | e.g. `farming`                                                     |
| created_at    | timestamptz | default `now()`                                                    |
| upgrade_level | integer     | 3.1 (used by 3.4). `0…10`, default 0, check                        |
| upgrade_pity  | integer     | 3.1 (3.4). Failed upgrades since the last success; default 0, `>= 0` |
| forge_secret  | uuid        | 3.1 (3.4). Server-only secret of the item's forge seed stream; default `gen_random_uuid()` |
| forge_counter | integer     | 3.1 (3.4). Draws taken from the item's forge seed stream; default 0, `>= 0` |
| reroll_count  | integer     | 3.1 (3.4). Affix rerolls done on the item; default 0, `>= 0`       |
| variant       | text?       | 3.1 (3.5). Null or game-core `ItemVariantId`; check `in ('void')`  |
| effect_id     | text?       | 3.1 (3.2). Legendary effect or Mythic signature in the effect registry |
| effect_roll   | double?     | 3.1 (3.2). The effect's rolled strength as a position in its range, check `0…1` |
| set_id        | text?       | 3.1 (3.3). Set id of a set piece                                   |
| mythic_id     | text?       | 3.1 (3.2). Named Mythic item id                                    |
| locked        | boolean     | 3.1 (3.7). Locked items can't be sold, salvaged or discarded; default false |

Indexes: `(character_id)`; partial unique `(character_id, equipped_slot) where equipped_slot is not null`. Checks: `item_level >= 1`, `upgrade_level` 0–10, the three counters `>= 0`, `variant`, `effect_roll`.

**`affixes` element** (`RolledAffix`): `{ affixId, tier, value }` plus two optional forge fields, absent on fresh affixes: `improvements` (integer ≥ 0, affix-improvement steps applied; the value stays inside its tier's `[min, max]`, so `validateItem` still holds) and `rerolled` (`true` when a reroll put this affix there). The API schema already serialises both.

#### Item model v2 (ticket 3.1): how Phase 3 builds on it
3.1 added every Phase 3 item column in one migration (`0011_item_model_v2`). **Tickets 3.2–3.7 add no item columns** (3.2 added only `activities.momentum`); they write these, and the API item view (`ItemView`) already returns `upgradeLevel`, `variant`, `effectId`, `setId`, `mythicId` and `locked` (the pity, forge and reroll counters and `effect_roll` stay server-side until the forge UI needs them; `forge_secret` never leaves the server). Game-core holds the matching types and constants (`items/model.ts`: `MAX_UPGRADE_LEVEL`, `ITEM_VARIANT_IDS`, `ItemProgressState`, `DEFAULT_ITEM_PROGRESS`).
- **3.2 Legendary / Mythic (done):** a Legendary drop stores its effect in `effect_id` and the rolled strength in `effect_roll` (the registry maps 0…1 to the effect's range, so retuning a range needs no data migration). A Mythic stores its named item in `mythic_id` (= its base id) and its fixed signature in `effect_id`; `effect_roll` stays null. Every insert of a generated item writes them (`itemEffectColumns`); merchant and forge spread the whole item. The item view now also returns `effectRoll` (the tooltip shows the rolled numbers). The crypt run snapshot stores each equipped item's `effectId`/`effectRoll` (older snapshots have none and replay without effects). Return-summary items carry `effectId`/`mythicId` when set.
- **3.3 Sets (done):** `set_id` marks a set piece (a Legendary on one of its set's fixed bases, without `effect_id`). Every insert of a generated item writes it (`itemEffectColumns`). Counting (`wornSets`) uses `set_id` and the base together, each piece once, never `variant`, so a Void piece counts as the same piece. The crypt run snapshot stores each equipped item's `setId` (older snapshots have none and replay without set bonuses); return-summary items carry `setId`. No column or migration was added.
- **3.4 Forge (done):** `upgrade_level` 0–10 raises the implicit (base) stats (`UPGRADE_IMPLICIT_BONUS`, +50 % at +10; +0 keeps the exact old expression); `upgrade_pity` counts failures since the last success and resets on success; `reroll_count` prices rerolls; affix state lives in the `affixes` elements (`improvements`, at most 3, the value stays in its tier; `rerolled`). **No save-scumming:** every random forge outcome draws from ``createRng(`${forge_secret}:${forge_counter}`)``, and the same transaction that pays and applies the result increments `forge_counter` (guarded by `where forge_counter = <read value>`). Lock order: idempotency key, character row, then the item row. A replayed or raced request sees the advanced counter and can never re-roll. The secret is a column of its own because the generation `seed` is not secret enough: merchant stock seeds derive from public inputs (character id and day), so a stream keyed on them could be predicted, and a player could spend a cheap action to skip a known failure. `forge_secret` is never sent to clients or written to the audit log; the counters stay server-side too, except through the Forge item view (`GET …/forge/items/:itemId`). The crypt run snapshot stores `upgradeLevel` (older snapshots replay at +0). No column or migration was added. Rules: `docs/ECONOMY.md`.
- **3.5 Void (done):** `variant = 'void'`, only on Legendary and Mythic items, set pieces included (game-core `activeVariant`/`validateItem`; elsewhere it is ignored). Every insert of a generated item writes it (`itemEffectColumns`). Forge work never changes it. The crypt run snapshot stores each equipped item's `variant` (older snapshots replay without Void); return-summary items and crypt claim result items carry `variant` (crypt result items now also carry `effectId`/`mythicId`/`setId` for the drop moment; older stored results have none). No column or migration was added. Prismatic is deferred; adding it later means widening the `variant` check and deciding the stacking rule (GDD §17).
- **3.6 Crypt tiers & targeted loot (done):** no item column. Migration `0013_dungeon_tiers` adds `dungeon_runs.tier`; `characters.progress` gains `cryptTierCleared` (jsonb, no migration); an Abbey contract's stored `reward.item` may be a targeted reward (`{ slot, rarityId, itemLevel, lootTableId }`), generated at the turn-in from a seed derived from the quest row id. That id is visible to the client, so the item can be predicted once the contract is taken; this is accepted: the reward is fixed at acceptance, contracts cannot be dropped or re-taken (one acceptance per slot and day), so knowing it early changes nothing. Items keep `source = 'quest'` / `'dungeon:namelessCrypt'`.
- **3.7 Lock:** sell, salvage, discard and the loot filter refuse `locked` items.
- None of these columns stamps game time, so `latestStoredTimeMs` (playtest clock) is unchanged.

### activities — implemented (1.6)
The character's current farming activity. Settlement rules: `docs/FARMING.md`.
| Column         | Type        | Notes                                                              |
| -------------- | ----------- | ------------------------------------------------------------------ |
| character_id   | uuid PK/FK  | → `characters.id` `ON DELETE CASCADE`; one activity per character  |
| account_id     | uuid FK     | → `accounts.id` `ON DELETE CASCADE`; **unique** (one farming character per account) |
| area_id        | text        | game-core `AreaId` of the cycle in progress; the server checks `isAreaUnlocked` before setting it (ticket 2.2) |
| pending_area_id | text?      | area switch requested mid-cycle (ticket 2.2): the cycle in progress finishes in `area_id`, then the settlement moves the activity here. Null = none |
| seed_secret    | text        | 128-bit random hex, never sent to clients; carried over in `characters.farm_state` |
| settlement_seq | integer     | settlements that credited time, `CHECK (>= 0)` (audit only)         |
| cycle_index    | bigint      | cycles completed with `seed_secret`, `CHECK (>= 0)`; cycle `i` uses RNG `${seed_secret}:${i}` (ticket 1.9) |
| started_at     | timestamptz | start (or last area switch)                                        |
| settled_at     | timestamptz | progress computed up to here (server clock); indexed for the scheduler |
| last_seen_at   | timestamptz | last client contact; offline credit ends at `last_seen_at + OFFLINE_CAP_SECONDS` |
| carry_ms       | integer     | `unusedMs` carried into the next settlement, `CHECK (>= 0)`        |
| health         | integer?    | health between settlements; null = full                            |
| momentum       | integer     | 3.2: Bloodrush stacks after the last cycle, default 0, `CHECK (>= 0)`; also saved in `characters.farm_state.momentum` (migration `0012_activity_momentum`) |
| summary        | jsonb       | rewards since the client last collected the return summary         |
| updated_at     | timestamptz |                                                                    |

Stopping deletes the row after saving `seed_secret`, `cycle_index`, `health` (and the unfinished cycle's area) to `characters.farm_state` (the audit log keeps the history). Per-settlement history lives in the audit log (`activity.reward`) rather than an `offline_settlement` table for now.

### character_materials — implemented (2.3)
Materials a character holds. Granted by settlement and forge salvage, spent by forge crafting (2.6).
| Column       | Type        | Notes                                                        |
| ------------ | ----------- | ------------------------------------------------------------ |
| character_id | uuid FK     | → `characters.id` `ON DELETE CASCADE`; PK with `material_id` |

| quantity     | bigint      | `CHECK (>= 0)`; stacks without a capacity limit for now      |

### dungeon_runs — implemented (2.5)
One dungeon run (`docs/DUNGEONS.md`). Claimed rows stay as history (the boss-loot cooldown reads them).
| Column             | Type        | Notes                                                                 |
| ------------------ | ----------- | --------------------------------------------------------------------- |
| id                 | uuid PK     | uuidv7                                                                |
| character_id       | uuid FK     | → `characters.id` `ON DELETE CASCADE`                                 |
| account_id         | uuid FK     | → `accounts.id` `ON DELETE CASCADE`; partial unique where `claimed_at is null` (one open run per account) |
| dungeon_id         | text        | game-core `DungeonId`                                                 |
| tier               | smallint    | game-core `DungeonTier` (ticket 3.6), default 1, `CHECK (1–3)`; part of the replay input |
| seed_secret        | text        | 128 random bits; never sent to clients                                |
| snapshot           | jsonb       | `{ classId, level, xp, equipment: [{ baseId, rarityId, itemLevel, affixes }] }` at the start |
| boss_loot_eligible | boolean     | off cooldown at the start                                             |
| started_at, ends_at | timestamptz | `CHECK (ends_at >= started_at)`; result claimable from `ends_at`     |
| claimed_at         | timestamptz | null = open                                                           |
| outcome            | text        | `cleared` / `failed`, set at the claim                                |
| boss_loot_granted  | boolean     | drives the cooldown                                                   |
| result             | jsonb       | the claim's result view                                               |
| created_at         | timestamptz |                                                                       |
Index `(character_id, started_at)`.

### character_quests — implemented (2.4)
Quests a character accepted (story chain and daily contracts, `docs/QUESTS.md`).
| Column        | Type        | Notes                                                                   |
| ------------- | ----------- | ----------------------------------------------------------------------- |
| id            | uuid PK     | UUIDv7; the id the client turns in                                      |
| character_id  | uuid FK     | → `characters.id` `ON DELETE CASCADE`                                   |
| kind          | text        | `story` / `contract` (`CHECK`)                                          |
| quest_id      | text        | game-core `StoryQuestId`, or the `ContractTemplate` id                  |
| contract_day  | text        | contracts only: UTC day `YYYY-MM-DD` (`CHECK`: set iff contract)        |
| contract_slot | smallint    | contracts only: board slot 0–2                                          |
| objectives    | jsonb       | game-core `QuestObjective[]`, copied at acceptance                      |
| progress      | jsonb       | `number[]`, per objective, capped at each target                        |
| reward        | jsonb       | game-core `QuestReward`, fixed at acceptance (contracts scale by level; since 3.6 an Abbey contract's item may be `{ slot, rarityId, itemLevel, lootTableId }`, the slot chosen) |
| status        | text        | `active` / `turnedIn` (`CHECK`; `turned_in_at` set iff `turnedIn`)      |
| accepted_at   | timestamptz |                                                                         |
| turned_in_at  | timestamptz |                                                                         |

Partial unique indexes: `(character_id, quest_id) WHERE kind = 'story'` (a story quest once), `(character_id, contract_day, contract_slot) WHERE kind = 'contract'` (a slot once a day). Progress is written only by settlement / dungeon events under the character lock; turn-in locks the row and flips the status in the reward transaction.

### idempotency_keys — implemented (2.6)
Stored responses of requests sent with an `Idempotency-Key` header (`apps/server/src/idempotency/`, `docs/API_CONVENTIONS.md`).
| Column       | Type        | Notes                                                                 |
| ------------ | ----------- | --------------------------------------------------------------------- |
| account_id   | uuid FK     | → `accounts.id` `ON DELETE CASCADE`; PK with `key`                    |
| key          | text        | the client's key (8–128 visible ASCII, a UUID by convention)          |
| request_hash | text        | SHA-256 of method, path and canonical JSON body                       |
| status_code  | smallint    | status of the stored response                                         |
| response     | jsonb       | the response body                                                     |
| created_at   | timestamptz |                                                                       |
| expires_at   | timestamptz | created + 24 h; indexed; expired rows are reused and pruned hourly by the settlement scheduler |

The row is claimed (inserted) at the start of the mutation's own transaction and filled in before it commits, so it exists only for committed successes.

### merchant_purchases — implemented (2.6)
Merchant offers a character bought; each daily offer sells once.
| Column       | Type        | Notes                                                          |
| ------------ | ----------- | -------------------------------------------------------------- |
| character_id | uuid FK     | → `characters.id` `ON DELETE CASCADE`; PK with `offer_id`      |
| offer_id     | text        | game-core offer id `<day>.<areaId>.<index>`                    |
| item_id      | uuid        | the item created (no FK: it may be sold or salvaged later)     |
| price        | bigint      | gold paid, `CHECK (>= 0)`                                      |
| created_at   | timestamptz |                                                                |

The primary key is the state guard behind the idempotency key: even without the stored response an offer cannot be bought twice.

## Relationships

```
account 1─* sessions
account 1─* character 1─1 activity
                     1─* dungeon_runs (≤ 1 unclaimed per account)
                     1─* item_instance (equipped_slot null = inventory)
                     1─* character_materials, 1─* character_professions
                     1─* character_quests
                     1─* currency_ledger
account 0..1─* audit_log
account 1─* idempotency_keys
character 1─* merchant_purchases
```
