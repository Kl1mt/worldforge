## Principles
- **Content is code, state is data.** Classes, enemies, areas, item bases, affixes and loot tables are versioned definitions in `@worldforge/game-core`, referenced from the database by string id (`class_id = 'warrior'`). The database stores only player and world *state*.
- **Server-authoritative.** Every row below is written only by the server. Values derived from content (final stats, power score) are computed, not stored, unless needed for leaderboards.
- **Integers for value.** Gold and other currencies are `bigint`; no floats for anything that is spent or compared.
- **Auditability.** Value-changing operations write a ledger/audit row in the same transaction.
- IDs are UUIDv7 (`uuid`), generated by the server (`uuidv7()` in `src/db/uuid.ts`); timestamps `timestamptz` in UTC. Soft deletes only where noted.
- Value-changing writes go through `withTransaction()` and write their audit row with `writeAudit(tx, …)` in the same transaction. Since ticket 3.8 they also record telemetry counters (`recordTelemetry(tx, now, …)`) next to the audit row; `withTransaction` writes them as the transaction's last statement (`docs/TELEMETRY.md`).

### sessions — implemented (1.1)
| Column     | Type        | Notes                                                             |
| ---------- | ----------- | ----------------------------------------------------------------- |
| id         | text PK     | SHA-256 hex of a random 256-bit token; the raw token only lives in the cookie |
| account_id | uuid FK     | → `accounts.id` `ON DELETE CASCADE`, indexed                      |
| created_at | timestamptz | default `now()`                                                   |
| expires_at | timestamptz | `CHECK (expires_at > created_at)`                                 |
| revoked_at | timestamptz | null while active; set on logout                                  |

A session is valid iff `revoked_at IS NULL AND expires_at > now()` (the server compares against its own clock). Login and registration insert a row (`created_at` = issue time, `expires_at` = + `SESSION_TTL_HOURS`); logout sets `revoked_at`. Ticket 5.7: a password reset revokes every session of the account, "log out other devices" every one but the caller's; the scheduler deletes expired sessions and sessions revoked more than 7 days ago, hourly, in batches of 5,000 (`pruneAuthRows`, real clock).

**`source`** values: `farming`, `dungeon:<dungeonId>` (a crypt or Watch chamber), `hoard:<dungeonId>` (a boss hoard; ticket T.1, before which hoard drops were stored as `dungeon:<id>`, which the backfill corrects where the stored run shows it), `forge` (crafted), `quest` (story and contract rewards), `merchant`. Game-core `itemBindingSource` maps them; anything else binds.

**`affixes` element** (`RolledAffix`): `{ affixId, tier, value }` plus two optional forge fields, absent on fresh affixes: `improvements` (integer ≥ 0, affix-improvement steps applied; the value stays inside its tier's `[min, max]`, so `validateItem` still holds) and `rerolled` (`true` when a reroll put this affix there). The API schema already serialises both.

#### Item model v2 (ticket 3.1): how Phase 3 builds on it
3.1 added every Phase 3 item column in one migration (`0011_item_model_v2`). **Tickets 3.2–3.7 add no item columns** (3.2 added only `activities.momentum`); they write these, and the API item view (`ItemView`) already returns `upgradeLevel`, `variant`, `effectId`, `setId`, `mythicId` and `locked` (the pity, forge and reroll counters and `effect_roll` stay server-side until the forge UI needs them; `forge_secret` never leaves the server). Game-core holds the matching types and constants (`items/model.ts`: `MAX_UPGRADE_LEVEL`, `ITEM_VARIANT_IDS`, `ItemProgressState`, `DEFAULT_ITEM_PROGRESS`).
- **3.2 Legendary / Mythic (done):** a Legendary drop stores its effect in `effect_id` and the rolled strength in `effect_roll` (the registry maps 0…1 to the effect's range, so retuning a range needs no data migration). A Mythic stores its named item in `mythic_id` (= its base id) and its fixed signature in `effect_id`; `effect_roll` stays null. Every insert of a generated item writes them (`itemEffectColumns`); merchant and forge spread the whole item. The item view now also returns `effectRoll` (the tooltip shows the rolled numbers). The crypt run snapshot stores each equipped item's `effectId`/`effectRoll` (older snapshots have none and replay without effects). Return-summary items carry `effectId`/`mythicId` when set.
- **3.3 Sets (done):** `set_id` marks a set piece (a Legendary on one of its set's fixed bases, without `effect_id`). Every insert of a generated item writes it (`itemEffectColumns`). Counting (`wornSets`) uses `set_id` and the base together, each piece once, never `variant`, so a Void piece counts as the same piece. The crypt run snapshot stores each equipped item's `setId` (older snapshots have none and replay without set bonuses); return-summary items carry `setId`. No column or migration was added.
- **3.4 Forge (done):** `upgrade_level` 0–10 raises the implicit (base) stats (`UPGRADE_IMPLICIT_BONUS`, +50 % at +10; +0 keeps the exact old expression); `upgrade_pity` counts failures since the last success and resets on success; `reroll_count` prices rerolls; affix state lives in the `affixes` elements (`improvements`, at most 3, the value stays in its tier; `rerolled`). **No save-scumming:** every random forge outcome draws from ``createRng(`${forge_secret}:${forge_counter}`)``, and the same transaction that pays and applies the result increments `forge_counter` (guarded by `where forge_counter = <read value>`). Lock order: idempotency key, character row, then the item row. A replayed or raced request sees the advanced counter and can never re-roll. The secret is a column of its own because the generation `seed` is not secret enough: merchant stock seeds derive from public inputs (character id and day), so a stream keyed on them could be predicted, and a player could spend a cheap action to skip a known failure. `forge_secret` is never sent to clients or written to the audit log; the counters stay server-side too, except through the Forge item view (`GET …/forge/items/:itemId`). The crypt run snapshot stores `upgradeLevel` (older snapshots replay at +0). No column or migration was added. Rules: `docs/ECONOMY.md`.
- **3.5 Void (done):** `variant = 'void'`, only on Legendary and Mythic items, set pieces included (game-core `activeVariant`/`validateItem`; elsewhere it is ignored). Every insert of a generated item writes it (`itemEffectColumns`). Forge work never changes it. The crypt run snapshot stores each equipped item's `variant` (older snapshots replay without Void); return-summary items and crypt claim result items carry `variant` (crypt result items now also carry `effectId`/`mythicId`/`setId` for the drop moment; older stored results have none). No column or migration was added.
- **6.4 Prismatic (done):** `variant = 'prismatic'`, only on Legendary and Mythic items, set pieces included (game-core `activeVariant`/`validateItem`; elsewhere it is ignored). Stacking rule (owner decision): one variant per item, never Void and Prismatic together; the column holds one value. Migration `0038_prismatic_variant` only widens `item_instances_variant_check` to `in ('void', 'prismatic')` (additive: every stored row stays valid). No new column: Prismatic's bonus is read from the stored affixes and the variant, which every snapshot (farm state, crypt runs, duels, the guild boss, board inputs) and item view already carry. Trading settings need no migration: a stored row without `tradeable.prismatic` reads its default (off).
- **3.6 Crypt tiers & targeted loot (done):** no item column. Migration `0013_dungeon_tiers` adds `dungeon_runs.tier`; `characters.progress` gains `cryptTierCleared` (jsonb, no migration); an Abbey contract's stored `reward.item` may be a targeted reward (`{ slot, rarityId, itemLevel, lootTableId }`), generated at the turn-in from a seed derived from the quest row id. Ticket 3.9: that id is visible to the client and the derivation is public, so the item could be computed as soon as the contract was taken (it could not be re-rolled: the reward is fixed at acceptance and contracts can't be dropped or re-taken). Since 3.9 a server-random `seed` is stored in `reward.item` at acceptance and stripped from every client view; rows accepted before 3.9 keep the row-id seed (jsonb, no migration). Items keep `source = 'quest'` / `'dungeon:namelessCrypt'`.
- **3.7 Lock & loot filter (done):** no item column. `locked` is set by `POST …/items/:id/lock|unlock` (idempotent, also on equipped items); sell, salvage (single and bulk, all or nothing) and discard answer `409 item_locked`, and `deleteItems` also requires `locked = false` as a backstop. Nothing consumes items as forge material (crafting uses materials only). The loot filter only ever sees new drops, so it can't reach a locked item. Rules live in `characters.loot_filter` (migration `0014_loot_filter`).
- **6.5b Awakening (done):** migration `0040_item_awakening` adds `awakening` and `awakened_at` (additive, null on every existing row). Every combat read carries `awakening` (whole-row reads for farming; the crypt/Tyrant run snapshot, the guild boss, scores and the duel snapshot select it; older snapshots have none and replay as before). Item views carry `awakening`/`awakenedAt` only when set.
- None of these columns stamps game time, so `latestStoredTimeMs` (playtest clock) is unchanged.

### game_settings — implemented (T.2)
- `game_settings (key text PK, value jsonb, version int check >= 1, updated_by FK accounts set null?, updated_at timestamptz)`: settings the owner changes in the admin panel without a deploy. One row per group: `trading` (game-core `TradingSettings`, docs/TRADING.md "Admin switches") and, since ticket 6.1, `leaderboards.formulas` (`{ switches: FormulaSwitch[] }`, the board formula switches planned between seasons, written by the server itself under an advisory lock and audited `leaderboards.formula_schedule`; read through `normaliseFormulaSchedule`, docs/LEADERBOARDS.md "Formula versions between seasons"; no migration). `value` is read through `normaliseTradingSettings`: a missing row or field is its default and a stored number above its hard maximum is clamped, so nothing needs a backfill. `version` goes up by one per change (optimistic concurrency: an edit names the version it was made from). ### trade_counters — implemented (T.4)
- `trade_counters (account_id FK accounts cascade, period text 'day'|'week', window_start date, metric text, direction text 'given'|'received'|'any', amount bigint check >= 0, updated_at timestamptz)`, PK `(account_id, period, window_start, metric, direction)`: what accepted trades moved for one account in one window (docs/TRADING.md "T.4 as built"). `metric` is game-core `TradeCapMetric` (`trades` per UTC day with direction `any`; `epic`, `legendarySet`, `mythicVoid`, `gold`, `commonMaterials`, `soulShards`, `abbeySilver` per UTC week, given and received apart); `window_start` is the day or the Monday the week starts on, from the accepting transaction's clock (the window rule). Written only by `commitTradeCounters` (check-then-increment under the accounts' `trade-counters:<id>` advisory locks, inside T.5's accept). Old windows stay for T.6's pattern report.
- `sanctions_kind_check` widened to allow `trade`.

Additive migration `0033_trade_rules` (one new table, empty; one widened check).

### trade_offers, trade_offer_lines, trade_holds — implemented (T.5)
- `trade_offers (id uuid PK, sender_account_id / receiver_account_id FK accounts restrict, sender_character_id FK characters restrict, receiver_character_id FK characters restrict null, status text, relation text, expires_at, closed_at, void_reason text null, void_detail jsonb null, created_at)`: one row per offer, kept forever (history, T.6). `status` goes once from `open` to `accepted`, `cancelled`, `declined`, `expired` or `void` (checks: the status list; `void` ⇔ `void_reason`; the two accounts differ). `receiver_character_id` is set at send when the offer asks for that hero's items, else at accept. `void_reason`: `switch`, `block`, `sanction`, `relation`, `deletion`; `void_detail` names the switches or the sanction kind. Indexes: `(sender_account_id, status)`, `(receiver_account_id, status)`, partial `(expires_at) where status = 'open'`. The `restrict` keys mean a hero or account an offer names can't be deleted before its offers are voided (`voidForDeletion`), so escrow can't be lost.
- `trade_offer_lines (id, offer_id FK cascade, side 'give'|'ask', kind 'item'|'material'|'gold', item_id uuid null (not a key: the item may later go), material_id null, amount bigint, snapshot jsonb null)`: the contents. An item line has amount 1 and the item's view at send as `snapshot`; material and gold lines a positive amount. The open offer's `give` gold and material lines **are** the escrow (that value has left the hero).
- `trade_holds (id, character_id FK cascade, account_id FK cascade, offer_id FK restrict, gold bigint >= 0, materials jsonb, item_ids jsonb, held_until, released_at null, created_at)`: what one hero received in one accepted trade. The gold and materials are in the hero's purse and stacks; while `held_until` is after the transaction's clock they can't be spent, traded or shelved (`heldValueOf`). `released_at` is set exactly once, with a `trade.release` audit row, after the hold ends (bookkeeping: spending never waits for it). Indexes `(character_id, held_until)`, partial `(held_until) where released_at is null`. Received items also carry `item_instances.hold_until`.

Additive migration `0034_trade_offers` (three new tables, empty; one nullable column, an index and a check on `item_instances` that every existing row satisfies, so no backfill).

**Ticket T.6** (migration `0035_trade_moderation`, additive, no backfill): `trade_offers.reversed_at timestamptz null`, `reversed_by uuid FK accounts set null`, `reverse_reason text null` (a moderator reversed the accepted trade; check `trade_offers_reversed_check`: only on `accepted`, the reason exactly with the time; status stays `accepted`); partial indexes `trade_offers_accepted_closed_idx (closed_at) where status = 'accepted'` and `trade_offers_reversed_idx (reversed_at) where reversed_at is not null`; `audit_log_trade_offer_idx ((data->>'offerId')) where event like 'trade.%'` (one trade's audit trail). A reversal sets `trade_holds.released_at` on the trade's open holds (with `trade.release`, `via: 'reverse'`); `heldValueOf` counts only holds with `released_at is null`.
