# Farming & offline progress (ticket 1.6)

Server-authoritative farming of an area (Phase 1: Abandoned Fields). Rules are pure functions in `packages/game-core/src/activity/`; persistence, locking and routes in `apps/server/src/activity/`. Endpoints: `docs/API_CONVENTIONS.md`. Table: `activities` in `docs/DATA_MODEL.md`.

## Lifecycle
- **Start** (`POST /api/characters/:id/activity`): only the account's active character, and only an area it has unlocked (`isAreaUnlocked` with the level after settling and `characters.progress`; otherwise `409 area_locked` with the blockers). One activity per account: starting one settles and stops the other. Same area again is a no-op; another area settles first, then switches (see "Area switches").
- **Settle** (`POST …/activity/settle`): credits elapsed server time and returns the return summary. Clients poll this during active play.
- **Scheduled settle**: every `SETTLE_INTERVAL_SECONDS` (default 300, `0` = off), the server settles activities not settled for one interval. That keeps rewards current while the player is away. It does not count as client contact.
- **Stop** (`POST …/activity/stop`): settles, returns the final summary, saves the farm state on the character and deletes the row.
- **Farm state survives stop/start (ticket 1.9).** Ending an activity (stop, or starting another character) saves `seed_secret`, `cycle_index` and `health` to `characters.farm_state`; the next start restores them. Without this, stop → start healed the character to full and re-rolled its next encounter: cycling it after every kill gave a level-1 mage 0 deaths and +25 % kills. Unsettled carry time is forfeited on stop. Health does not regenerate while stopped (the first search of the next cycle regenerates as usual).
- **Equipment changes settle first (ticket 1.9).** Equip, unequip and discard settle the running activity (with client contact) before changing anything, so the time before the change is credited with the gear and inventory that were really there: no swapping in a gold-find set just before settling, and no discarding to dodge the capacity rule retroactively.

## Area switches (ticket 2.2)
An area switch never re-simulates a cycle in another area. The server settles first (like the equipment rule), then applies game-core `requestAreaChange`:
- **Between cycles** (`carry_ms = 0` and nothing pending): the switch takes effect at once.
- **Mid-cycle** (`carry_ms > 0`): the switch becomes pending (`activities.pending_area_id`). The cycle in progress finishes in the old area; `settleFarming` (`switchToAreaId`) runs that one cycle there (`maxCycles: 1`) and every later cycle of the window in the new area. If the window ends first, nothing switches and the whole window is carried as usual. The settlement then sets `area_id`, clears `pending_area_id` and writes `activity.start` with `deferred: true`.
- Choosing the current area again cancels a pending switch; choosing another area replaces the target.
- **Stop mid-cycle → start elsewhere:** the unfinished cycle's area is saved in `farm_state.areaId`. The next start creates the activity in that area with the requested one pending, so the forfeited cycle replays from its start in the same area (same seed, index and state: the same outcome) before the hero travels. While such a bound cycle is pending, a new request only re-targets the switch, even with no time in the cycle yet.

So each cycle index is simulated in exactly one area, a player cannot dodge a long or deadly fight in progress by switching (or stop/start-ing) to another area, and — because the switch point is always a settlement — a run with switches gives the same result however often the client settles. Tests: `area switches` in `packages/game-core/src/activity/activity.test.ts` (settle every 1 s / 3.3 s / 60 s / once, with three switches incl. a re-target) and `areas & unlocks (ticket 2.2)` in `apps/server/src/activity/activity.test.ts` (two clients with the same seed, one settling every 5 s, the other only at the switches: identical characters, items and activity rows); real-Postgres race of switches and settles in `concurrency.pg.test.ts`.

## Time and the offline cap
- Credited window = `[settled_at, min(now, last_seen_at + OFFLINE_CAP_SECONDS)]`, server clock only. Later time earns nothing and is reported as `cappedMs`. `settled_at` then moves to `now`.
- Client contact (start, settle, stop) moves `last_seen_at` to `now` after settling. While the client keeps settling, nothing is capped. A player who is away earns at most 3 h (`OFFLINE_CAP_SECONDS`, default 10800) however many scheduled settlements happen.
- **Active vs offline (Phase 1 rule):** the reward rate is the same. Active play is "more efficient" only because it never hits the cap. Active-only bonuses come with later activities (GDD §9.2).
- `unusedMs` (an unfinished cycle at the window end) is stored as `carry_ms` and added to the next window. No time is lost or awarded twice.

## Settlement (`settleFarming`, game-core)
- Inputs: class, level, xp, health, equipped items, area, server seed, window (incl. carry), inventory count. No client input reaches it.
- Combat: one `simulateFarmingAggregate` over the whole window with **per-cycle RNG**: cycle `i` (global index, `activities.cycle_index` + position) draws from `${seed}:${i}`.
- Loot: one `rollLoot` per kill, RNG `${seed}:loot:${i}` for the kill's cycle. The source level is the character's level at the start of that cycle, clamped to the area's enemy levels.
- **Splitting a window changes nothing (ticket 1.9).** The unfinished cycle at the window end is not applied; its time is carried and the next settlement replays it with the same streams and the same starting state. Settling every second gives exactly what one settlement at the end gives (game-core tests pin this). Before ticket 1.9, each settlement re-rolled the unfinished cycle, so settle spam avoided deaths and long fights (≈ +20 % kills).
- **Equipment → stats:** `itemContribution` / `equipmentModifiers` sum implicit stats and affixes. Core stats go to `deriveCharacterStats`. **Gold find is summed, then capped** at `modifierCaps.goldFind` (default +100 %) before `rollLoot` (GDD §6.2).
- **Seed:** `seed_secret` (128 random bits, never sent to clients) plus `cycle_index`. Same secret, index, state and window give the same result (tests pin this). `settlement_seq` is kept for the audit log only.

## Gathering & professions (ticket 2.3)
Gathering is part of the per-cycle settlement; rules in `packages/game-core/src/professions/`, persistence in `apps/server/src/materials/`.
- **Per cycle.** Every committed cycle the hero survives (kill or timeout; not a death) rolls each of the area's yields (`DEFAULT_PROFESSION_CONFIG.areas`) from its own stream `${seed}:gather:${i}`. Undead kills also roll the area's undead drops (`soulShard` in the Old Burial Grounds, 3 %; no profession). Each yield always consumes the same draws, so one node never shifts another's roll.
- **Profession level raises yield, not the find rate:** a find gives `1 + 0.02 · (level − 1)` units (the fraction is a chance of one more), so level 50 roughly doubles it. Profession XP per unit by rarity (common 15, uncommon 20, rare 50); `xpToNext(l) = round(230 · l^0.7)` (ticket B.1), cap 50. XP is applied per cycle, so later cycles of the same window use the new level.
- **Split- and switch-invariant.** Like loot, the unfinished cycle gathers nothing until it is committed, and the profession state is carried from settlement to settlement, so settling every second gives exactly what one settlement gives, also across area switches (game-core `settlement splitting` and `area switches` tests include materials and professions; server: `materials & professions (ticket 2.3)` and the 2.2 switch invariance test compare the stored rows).
- **Persistence.** The settlement transaction reads `character_professions` (under the character lock), runs `settleFarming` with those levels, then adds materials to `character_materials` (`quantity = quantity + n`) and writes the changed professions, together with XP, gold, items, the activity row and the `activity.reward` audit entry (which now lists `materials`). The real-Postgres race test checks that eight parallel settles grant exactly what one settlement of the same seed grants.
- **Summary.** `summary.materials` (`{ materialId: n }`) and `summary.professions` (`{ professionId: { xpGained, levelsGained } }`); missing in summaries written before 2.3.
- Numbers (ticket B.1, `docs/ECONOMY.md`): commons and iron ore at 5–6 % per cycle, abbey silver 0.8 %. A hero runs ~550–600 cycles an hour, so a common stack grows by ~100 per 3 h cap and a profession by 3–4 levels from level 1.

## Inventory capacity
`inventory.capacity` (default 60 unequipped items). Since ticket 3.7 the character's loot filter is applied first (`docs/LOOT.md` "Loot filter"): a drop it sells or salvages takes no space, its gold is part of the settlement's gold and its materials go to the stacks (not to gathering). The summary reports them in `filtered` (`{ sold, salvaged, gold, materials }`, absent while nothing was filtered). Other drops beyond the free space are **auto-salvaged to gold**: `round((0.5 + 0.15 · itemLevel) · rarity)` (ticket B.1), rarity × 1/2/4/8/16/32 from common to mythic. The summary reports `itemsSalvaged` and `goldSalvaged`. All values are in `DEFAULT_ACTIVITY_CONFIG`.

**Valuable drops survive a full pack (ticket B.2, owner decision).** A Legendary, a Mythic, a set piece or a Void item (`isValuableDrop`: exactly the loot filter's protected categories) that finds no free slot is **kept beyond the capacity** instead of being salvaged. The pack is then *over capacity* (e.g. 63 / 60). That changes nothing else: ordinary drops keep being salvaged while the pack has no free slot (as on a full pack), and buying, crafting and item quest rewards keep refusing a pack without a free slot (`inventory_full`), as before. Equip, unequip, sell, salvage and discard work as usual, and every sale brings the pack back toward the limit. Order per drop, in drop order (`createDropPlacer`): (1) the loot filter, so a player who ticked a protected category still has those drops sold or salvaged; (2) a free slot; (3) a valuable drop goes over the capacity; (4) anything else is salvaged to gold. Deterministic and split-invariant: the placement depends only on the pack count at the start of the window and the drop order, and a settlement hands its new count (over capacity included) to the next one (game-core test: a 6 h Abbey window settled every 20 minutes keeps and salvages exactly the same items as one settlement). The summary reports `itemsOverCapacity` (part of `itemsGained`); the audit row `activity.reward` carries `itemsOverCapacity` when it is non-zero. The crypt claim follows the same rule for every tier (`itemsOverCapacity` in the claim result and `dungeon.claim`). Only drops are concerned: merchant purchases, crafts and quest rewards still need a free slot.

## Concurrency and idempotency
Each settlement runs in one transaction. It locks the `characters` row (`SELECT … FOR NO KEY UPDATE`), then the `activities` row (`FOR UPDATE`). Start also locks the `accounts` row first; inventory changes lock the character, then settle. Account and character locks use `FOR NO KEY UPDATE` (ticket 1.9): it serialises these transactions just like `FOR UPDATE`, but does not conflict with the `FOR KEY SHARE` locks that foreign-key checks take when an audit, activity or item row is inserted, which deadlocked start (account → character) against stop/settle (character → account). These races are tested against a real PostgreSQL server with parallel transactions (`apps/server/src/concurrency.pg.test.ts`, ticket 1.9), not only on PGlite. A concurrent settle waits, then sees the moved `settled_at` and credits ~0, so a window is never credited twice. XP, level, gold (`gold = gold + n`), item rows, the activity row and the `activity.reward` audit entry commit together.

## Return summary
`activities.summary` accumulates every settlement since the client last collected it: settlements, simulated/capped ms, kills, deaths, XP, levels, gold (incl. salvaged), items gained (last 100 listed) and salvaged. `settle` returns it with `since`/`until` and starts a new one. Rewards are already granted when it is computed, so a lost response loses only the summary, never the loot.

## Open points
- Health persists between settlements and across stop/start; regeneration while stopped is not modelled.
- Accepted residual (ticket 1.9): a change of equipment re-simulates the unfinished cycle with the new stats (same RNG stream, different outcome). Players cannot see an unfinished cycle's outcome. The area half of this residual is closed by ticket 2.2 ("Area switches").
- Item ids in the summary may refer to items discarded since (ticket 1.7).
- Per-settlement history beyond the audit log (an `offline_settlement` table) is deferred.

## Bloodrush momentum (ticket 3.2)
A kill streak from the Bloodrush effect is carried between cycles like health: `activities.momentum` after each settlement, `farm_state.momentum` across stop → start. Only committed cycles change it, so settlement splitting stays invariant (tested in game-core and the server).
