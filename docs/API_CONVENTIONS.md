# API conventions

Applies to every endpoint served by `apps/server`. Implemented so far: health, content, the account/auth endpoints (ticket 1.2), the character endpoints (ticket 1.3), the farming endpoints (ticket 1.6), the inventory & equipment endpoints (ticket 1.7), the merchant and forge endpoints with the `Idempotency-Key` mechanism (ticket 2.6; forge upgrades, rerolls and affix improvement in 3.4), the quest endpoints (ticket 2.4), the 404 handler and the error handler (`apps/server/src/errors.ts`; throw `ApiError(status, code, message, details?)` for deliberate failures).

## Basics
- REST over HTTPS, JSON request and response bodies (`application/json; charset=utf-8`).
- Everything lives under `/api`. Breaking changes get a new prefix (`/api/v2`) rather than silently changing shapes; additive changes (new fields) are allowed.
- Resource paths are plural nouns in kebab-case: `/api/characters/:characterId/inventory`. Actions that are not plain CRUD use a verb sub-resource: `POST /api/characters/:id/activity`.
- JSON fields are `camelCase`. IDs are opaque strings (UUIDv7). Timestamps are ISO 8601 UTC strings (`2026-11-04T12:00:00.000Z`). Money-like values (gold) are integers, never floats.
- Methods: `GET` (safe, cacheable), `POST` (create or action), `PATCH` (partial update), `DELETE`. `PUT` is avoided.

## Success responses
- `200` with the resource or result object; `201` for creation (with the created resource); `204` with no body for deletions.
- Bodies are objects, never bare arrays, so fields can be added later: `{ "items": [...], "nextCursor": "..." }`.
- Lists use cursor pagination (`?cursor=&limit=`), default limit 50, max 200.

## Error envelope
Every non-2xx response has this shape:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Human-readable summary, safe to show in a log or dev tool",
    "details": {}
  }
}
```

- `code` is a stable, machine-readable snake_case identifier; clients branch on it, never on `message`.
- `details` is optional (e.g. per-field validation errors).
- 5xx responses never leak internals: they return `internal_error` and the real error is logged with the request id.

| Status | Typical `code`                   | Meaning                                                     |
| ------ | -------------------------------- | ----------------------------------------------------------- |
| 400    | `validation_failed`              | Body/query/params failed schema validation                  |
| 401    | `unauthenticated`                | No or invalid session                                       |
| 403    | `forbidden`                      | Authenticated, but not allowed (not used for other accounts' resources, see 404) |
| 404    | `not_found`                      | Route or resource does not exist — **also for another account's resource** (ticket 1.9), so ids can't be probed |
| 409    | `conflict` / `idempotency_conflict` | State conflict, or idempotency key reused with another body |
| 422    | domain codes, e.g. `slot_mismatch`, `insufficient_gold` | Valid request that the game rules reject |
| 429    | `rate_limited`                   | Too many requests                                           |
| 500    | `internal_error`                 | Unexpected server error                                     |

## Validation
- Every route declares JSON Schemas for `params`, `querystring` and `body` (Fastify's built-in Ajv). Unknown body properties are rejected (`additionalProperties: false`; `buildApp` sets Ajv's `removeAdditional: false` so they are not silently stripped). Response schemas are declared so serialisation strips unexpected fields.
- **Numbers are finite** (ticket 4.11): after validation a root `preHandler` refuses any non-finite number in the query, params or body (`400 validation_failed`, `details.fields`). Ajv's coercion turns `?since=1e309` or `Infinity` into `Infinity`, which passes `integer` (and even `maximum`), and JSON parses `1e309` the same way; such values used to reach PostgreSQL and answer `500`.
- Schema validation only checks shape. Game rules (ownership, slot eligibility, affordability, cooldowns) are checked on the server against stored state and return `4xx` domain codes.
- The server never accepts client-computed outcomes: no currency amounts, item rolls, combat results, damage numbers or scores in request bodies (GDD §16.3). Clients send intents and IDs only.

## Idempotency
Implemented in ticket 2.6 (`apps/server/src/idempotency/`). Endpoints that are idempotent by state keep working without the header (Phase 1, ticket 1.9 review): settle credits elapsed server time once (row locks; a repeat credits ~0 and returns an empty summary); start is a no-op for the same area; stop/settle without an activity answer `409 not_farming`; equip into the current slot and unequip of an inventory item are no-ops; a second discard of the same item is `404`; register and character creation are guarded by unique indexes (`409`).

Endpoints that grant, spend or move value and are **not** repeat-safe by state require an `Idempotency-Key` header: merchant buy and sell, forge salvage and craft (2.6), forge upgrade, reroll and improve (3.4); quest turn-in and dungeon claim (2.4, 2.5) use the same helper. Ticket 5.5: duels (`POST /api/arena/duels`) too, although they move no value: the key is what stops a retry or a replay from re-rolling a duel (the same key always answers the stored duel).

- The client sends a fresh UUID per intended action and reuses it only to retry that same action after a network error or a 5xx (the web client's `ActionKeys`). Keys are 8–128 visible ASCII characters; a missing key is `400 idempotency_key_required`, a malformed one `400 validation_failed`.
- Handlers call `idempotentTransaction(app, request, reply, { now }, fn)` instead of `withTransaction`. It inserts `(accountId, key, request hash)` into `idempotency_keys` at the start of the mutation's transaction, runs `fn`, and stores the response before commit. The request hash covers method, path and the canonical JSON body.
- A retry with the same key and request returns the stored status and body with `Idempotency-Replayed: true`, without running the handler. A concurrent duplicate waits on the key's unique index until the first commits, then replays. The same key with another method, path or body is `409 idempotency_conflict`.
- Only successes are stored: a failed request rolls back the claim with everything else, so it changed nothing and may be retried with the same key.
- Keys are per account and live 24 hours; an expired key is taken over by a new request, and the settlement scheduler prunes expired rows hourly.
- Value grants are additionally guarded by state (row locks, `merchant_purchases` primary key, `CHECK` constraints on gold and material quantities), so a lost idempotency record cannot duplicate value.

## Auth & sessions
- Session via the `wf_session` cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api`, expiring with the session. The value is a random 256-bit token; the database stores only its SHA-256 (`sessions.id`).
- Routes that need a player use `preHandler: app.requireAccount`, then read `request.auth.account` (and `request.auth.sessionId`). It answers `401 unauthenticated` and clears a stale cookie when the session is missing, unknown, revoked or expired. No route trusts an account or character id from the body without an ownership check.
- Sessions have a fixed lifetime from login (`SESSION_TTL_HOURS`, default 30 days; no sliding renewal yet). Logout revokes the row (`revoked_at`) and clears the cookie.
- Failed logins always return the same `401 invalid_credentials` body, whether the email is unknown or the password is wrong, and unknown emails still run an argon2 verification so timing matches. Registration does reveal `409 email_taken`; it is rate-limited (sending a "you already have an account" letter instead is a possible follow-up now that mail exists).
- **Per-account login throttling** (ticket 5.7, `auth/login-throttle.ts`), on top of the per-IP limit: keyed by the normalised email the attempt names, known or not. 5 failures are free; each further failure locks the address for 30 s, doubling to at most 15 minutes; an hour without failures, a successful login or a password reset starts it fresh. While locked, login answers `429 rate_limited` with `Retry-After` and `details: { retryAfterSeconds, limit: 'account' }` before checking the password, the same for every address. Audit `auth.login_locked` when a lock starts; telemetry `auth.login` (`ok`, `failed`, `locked`, `throttled`). A wrong current password on the email change counts too. In-process memory like the other limits.
- **Email verification and password reset** (ticket 5.7, `auth/security-routes.ts`, SECURITY.md "Accounts"): mailed single-use tokens (verify 24 h, reset 30 min; hashed at rest; only the newest of each purpose works). Invalid, used or withdrawn: `400 token_invalid`; expired: `400 token_expired`. Without mail configured, `forgot-password` and the resend answer `503 email_unavailable` (the same for every address); nothing else changes. `forgot-password` always answers `202 { accepted: true }` and is padded to at least 400 ms, so known and unknown addresses look alike; at most 3 reset letters per address an hour (beyond that the same `202`, no letter). Letters (`account.verification_sent`, resend and email change: 3 per account an hour) over: `429 rate_limited`, `details.limit: 'mail'`. Mails are sent after the request (never awaited).
- Rate limits (`@fastify/rate-limit`, per client IP, in-process memory): login 10/minute, register 5/hour. Over the limit: `429 rate_limited` with `Retry-After` and `details.retryAfterSeconds`. Behind a reverse proxy set `TRUST_PROXY=1` so the IP comes from `X-Forwarded-For`.
- **Per-account rate limits** (ticket 3.9, `apps/server/src/auth/account-rate-limit.ts`): every route behind the session check (all `/api/account*` and `/api/characters*` routes) counts against the session's account, whatever the character, tab or IP: **900 requests and 300 actions (any method but `GET`/`HEAD`) per account per minute** (fixed window on the real clock, never the scaled playtest/e2e farming clock; in-process memory, so one API instance). That fits three tabs of busy play (each tab polls with POSTs: settle every 8 s, a crypt run every 2 s; plus a click a second). Over either limit: `429 rate_limited` with `Retry-After` (seconds until the window ends) and `details: { retryAfterSeconds, limit: 'requests' | 'actions' }`. The check runs before any game work and before the `Idempotency-Key` is claimed, so a refused request changes nothing and the same key can be retried after the wait; refused requests are not counted. Unauthenticated requests answer `401` and are not counted. Configurable per app (`auth.accountRateLimit`); rewards never depend on request frequency, so the limits only bound database time per account (before trading and leaderboards).

- **Suspensions** (ticket 4.1): `requireAccount` answers `403 account_suspended` (`details.sanction`) for every request of a suspended account, and login refuses it after a correct password. **Social writes** (reports, the forced rename; later profile, friend, guild and chat writes) go through `socialWrite` (`docs/SOCIAL.md`): a tighter per-account class, **12 a minute and 240 an hour**, `429 rate_limited` with `details.limit: 'social'`, and `403 muted` while muted. **Trade writes** (ticket T.4, T.5's offer routes) go through `tradeWrite`: their own class, **20 a minute**, `429 rate_limited` with `details.limit: 'trade'`; at accept a cap that would be broken is `409 trade_cap_reached` with `details.refusals` (your own with `used`, `adding`, `max`, `resetsAt`; the other account's naming only the cap). Moderator routes (`/api/mod/*`) answer the not-found handler's exact `404` to anyone who is not staff, before body validation. Ticket 4.11: every other path under `/api/mod/` and `/api/admin/` goes to a catch-all behind the same `onRequest` check, so a malformed body cannot tell a real staff route from a missing one, and `Cache-Control: no-store` is set on admin answers only (it was on the 404 too).
- **Admin routes** (ticket D.3, `/api/admin/*`, `apps/server/src/admin/`): the scope's `onRequest` hook `app.requireAdmin` answers the not-found handler's exact `404` to anyone who is not an admin (anonymous, player, moderator), before body validation; admins then pass `requireAccount`, so 3.9's per-account limits, the suspension check and presence apply. Mutations re-read the admin's role under a share lock in their transaction. Every response is `Cache-Control: no-store`. `GET /api/admin/telemetry?reconcile=true` has its own stricter class (**3 per 5 minutes** per admin, `429 rate_limited` with `details.limit: 'reconcile'`), since it scans the audit log. There is **no route that grants or revokes a role**.

## Observability
- Each request gets a request id (Fastify `reqId`), included in logs; later echoed as `X-Request-Id`.
- Structured JSON logs (pino). No personal data beyond the account id in logs.

## Admin tools (ticket D.4)

Under D.3's `/api/admin` scope: the not-found `404` for everyone but admins (before body validation), `no-store`. Every **write** needs an `Idempotency-Key` and a `reason` (3–500 characters), re-reads the admin's role in its transaction, and writes one `admin.*` audit row on the target account (docs/SOCIAL.md "Admin tools"). Destructive writes take `confirm`: the hero's name, the handle (shelf items, sessions) or the flag id, compared ignoring case (`422 confirmation_mismatch`). Cheat tools on a normal account other than the admin's own: `403 test_account_required`; on the admin's own non-test account the answer has `warning: 'public_boards'`.

| Route | Kind | Body / answer |
|---|---|---|
| `GET /admin/accounts/:handle` | read | `{ account }`: the inspector's account file (no email; `emailVerified` only) |
| `GET /admin/accounts/:handle/heroes/:id/view` | read | read-only hero sheet (`readOnly: true`; no settlement, no write) |
| `POST …/heroes/:id/items/preview` | read | `{ baseId, rarityId, itemLevel, variant, upgradeLevel, seed? }` → `{ seed, item }` (no key needed) |
| `POST …/heroes/:id/items/grant` | cheat | the same plus `seed`, `reason` → `{ item }`; `422 invalid_item` (`details.problems`), `422 inventory_full` |
| `POST /admin/accounts/:handle/items/:itemId/remove` | support | `{ confirm, reason }` → `{ removed: { location } }`; `409 item_held`, `409 item_in_escrow` |
| `POST …/heroes/:id/gold` · `…/materials` | grant: cheat; refund, remove: support | `{ mode, amount \| materials, confirm? (remove), reason }`; `422 insufficient_gold` / `insufficient_materials` (also into held value) |
| `POST …/heroes/:id/xp` · `…/level` | cheat | `{ xp }` (game-core `applyXp`) · `{ level }` (XP 0) |
| `POST …/heroes/:id/delete` · `…/restore` · `…/rename` | support | `{ confirm, reason }` · `{ reason }` (`409 restore_window_passed`, `no_free_slot`) · `{ name, reason }` (`409 name_taken`); delete: `409 shelf_not_empty` |
| `POST …/heroes/:id/progress` · `…/professions` · `…/daily-reset` | cheat | `{ gravewardenDefeated, cryptTierCleared, ashenWardenDefeated, forgeTyrantDefeated? }` (6.2: optional, absent = unchanged) · `{ professions: { id: level } }` · `{ limits: ['ratedDuels' \| 'contracts' \| 'merchant'] }` |
| `POST …/heroes/:id/quests/:questRowId/complete\|reset` | cheat | `{ reason }`; complete fills the objectives (the player turns it in), reset deletes the row |
| `POST …/heroes/:id/fast-forward` | cheat | `{ minutes }` (1 … the offline cap): moves the activity's clock back, then the normal settlement; `409 no_activity` |
| `POST /admin/accounts/:handle/sessions/revoke` · `…/login-lock/clear` | support | `{ confirm, reason }` → `{ revoked }` (keeps the admin's own current session) · `{ reason }` |
| `GET /admin/world` | read | world flags, scheduler state, seasons, deleted heroes due for purge |
| `POST /admin/world/flags/:flagId` | world | `{ set, confirm, reason }` |

Lock order of every write: the shelf lock and the target account row (`for no key update`) when needed, the admin's row (`for share`), the hero (`lockOwnedCharacter`, settling first), its items. Deletion also runs T.5's and T.7's seams (docs/TRADING.md "Hero deletion").
